## はじめに

こんにちは。Shizen Connectの佐藤です。

私は現在エネルギーマネジメントシステムを支えるエッジ端末「Shizen Box」を開発しています。
Shizen Boxは、太陽光発電や蓄電池などの複数のプロトコル機器との接続・連系制御を担うデバイスです。

本連載では、私がペンテスト対応した実務経験をもとに、設計・実装・運用の観点で得られた知見を整理しています。

## ペンテストで実施したこと

ペンテストは第三者機関に依頼して、大きく以下の4つを実施してもらいました。
IoTデバイスのリスクを情報セキュリティの三要素（機密性・完全性・可用性）でざっくり分けて、それぞれに対応するテストを当てたイメージです。

| テスト | 主に見たリスク | 実施内容 | 結果 |
|-------|-------------|---------|------|
| タンパテスト | 機密性（情報漏洩） | eMMCへ直接結線してUSBブートを試行 | 問題なし |
| DoS/DDoS攻撃 | 可用性（サービス停止） | SYNフラッド攻撃、ICMPブロードキャスト攻撃 等 | 問題なし |
| ファジングテスト | 完全性（改ざん・不正操作） | ECHONET Lite / Modbus TCP の通信を偽装して送信 | 問題なし |
| 侵入テスト | 機密性・完全性 | IP通信、シリアルデバッグインタフェース、WebUIからの侵入を試行 | U-Boot、WebUIで計2件の指摘 |

結果として、4つのうち3つは特に問題なし、侵入テストで2件の指摘を受けた、という形になりました。

ちなみに、ペンテスト期間中は第二回で紹介した早期検知の仕組み（iptablesのLOGで特定ポートへのアクセス試行を記録して、チャットツールへ通知する仕組み）をそのまま使っていました。
テスト機関がいつ攻撃を始めたのか、どのポートが狙われているのかがリアルタイムで見えていたので、想定外の挙動があってもすぐ動ける状態にできていたのは精神衛生上かなり良かったです。

## 1.タンパテスト

タンパテストは、デバイスが物理的に攻撃者の手に渡ったときに、機密情報を抜き取られないかを確認するテストです。
Shizen Box は一般家庭やフィールドに設置されるデバイスなので、盗難や中古流通も考えると、ネットワーク越しの攻撃とは別にここは見ておく必要があると思っています。

今回は、基板上のeMMCへ実際に結線してUSBブートを試み、eMMCの中身にアクセスできないかを確認してもらいました。
テスト機関が基板を必要以上に壊さずに済むように、eMMC周りのパターン図やデータ線へのアクセス方法は事前にこちらから提供しています。

その結果、物理アクセスによる機密情報の搾取につながる問題は確認されませんでした。

---

## 2.DoS/DDoS攻撃

可用性の確認として、DoS（Denial of Service：サービス妨害）攻撃も試してもらいました。

実施したのは以下の2つです。

- SYNフラッド攻撃：TCPの3ウェイハンドシェイクを途中で放置させて、接続待ちのリソースを枯渇させる攻撃
- ICMPブロードキャスト攻撃：ブロードキャストアドレス宛てにICMPエコー要求を投げて、大量の応答を発生させる攻撃（いわゆるSmurf攻撃）

これらを受けている最中にサービス停止などの異常が生じないか、攻撃が止んだあとに正常に戻るかを確認した結果、特に問題は確認されませんでした。
第二回で紹介したカーネルレベルのDoS対策（SYN Cookies や ICMP の応答制御など）がちゃんと効いていたことが確認できたのは、素直にうれしかったです。

---

## 3.ファジングテスト

ファジング（Fuzzing）は、わざと不正な形式や想定外の値のデータを大量に入力して、プログラムの異常動作や脆弱性を見つける手法です。
このあたりはIPAが分かりやすい手引きを公開しているので、詳しくは末尾の参考資料に譲ります。

Shizen Box は、エネルギー機器との通信に ECHONET Lite と Modbus TCP を使っています。
今回は、第三者機関側で実装したファザー（ファジング用のプログラム）から Shizen Box 2 に向けて、ECHONET Lite / Modbus TCP の通信ヘッダ等を偽装したパケットを送り込み、なりすましによって通信異常が生じないかを確認してもらいました。

ファザーを実装に合わせて作り込んでもらうため、対応しているModbusのファンクションコードやレジスタマップ、ECHONET Liteの対応オブジェクトやプロパティ一覧、正常系の通信シーケンスといった実装仕様はこちらから提供しています。
ここをちゃんと渡しておかないと汎用的なファジングで終わってしまい、実装固有の弱いところまで届かないので、地味に重要なところだと思っています。

結果、特に問題は確認されませんでした。
プロトコル実装は自分たちで書いている部分も多いので、ここが無事だったのは正直ほっとしました。

## 4.侵入テスト

最後が侵入テストです。
テスト機関には事前に「守るべき機密情報のリスト」（認証情報、設定ファイル、ログなど）を渡していて、それらが不正アクセスで奪われたり書き換えられたりしないか、という観点で攻めてもらっています。

まず、IP通信による侵入は、第二回で紹介したファイアーウォールで不要なポートを閉じていたこともあり、侵入不可であることが確認されました。

次に、シリアルデバッグインタフェースからの侵入です。
こちらも第二回で紹介した通り、通常のシリアルコンソールは論理的に無効化する対策を施していたので、パスワード認証の画面にもたどり着けず、問題なしでした。

ところが、U-Boot経由でファイルシステムへのアクセスが成立する、という指摘を受けました。
OS側の入口は塞いでいたものの、その手前のブートローダ側が開いていた、という形です。

もう1件はWebUIです。
Shizen Box 2 のWebUIは一般ユーザーには公開していないメンテナンス用の画面で、通常は外部から到達できない構成になっています。
ペンテストでは、WebUI自体の作りを確認してもらうため、到達可能な状態にしてテストしてもらいました。
その結果、管理者ではないユーザーでログインした状態から、管理者パスワードを書き換えられてしまう、という指摘を受けました。

以降では、この2件について、指摘内容と対策を順に紹介します。

## 脆弱性1：U-Bootコンソールへの認証なしアクセス

- [CVE-2026-80253](https://www.cve.org/CVERecord?id=CVE-2026-80253)：不適切な物理アクセス制御（CWE-1263）
- CVSS v3.0：6.8（`CVSS:3.0/AV:P/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`）
- CVSS v4.0：7.0（`CVSS:4.0/AV:P/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N`）

### 何が問題だったか

Shizen Box 2 の起動プロセスでは、U-Bootコンソールに入るための認証が設定されていませんでした。
なので、シリアルデバッグインタフェースに物理的にアクセスできれば、U-Bootコンソールに入れてしまう状態でした。

U-Bootコンソールに入られると、起動パラメータを書き換えてOS側のログイン認証を回避できてしまいます。
そうなると、ファイルシステムの抜き出しも改ざんもできてしまうので、認証情報や鍵が漏れる前提で考える必要があります。

### 物理アクセスは想定していたが、U-Bootが抜けていた

第二回で書いた通り、Shizen Box は一般家庭やフィールドに設置されるデバイスなので、攻撃者が物理的に機器に触れるという前提は最初から捨てていませんでした。
そのため、OSのシリアルコンソールはキッティング完了時に論理的に塞ぐ対策を施していて、実際にペンテストでもそこからは入れないことが確認できています。

ただ、U-Bootからのアクセスについては対策が間に合っておらず、ペンテストでまさにそこを突かれた形になりました。
物理アクセスを想定して入口を塞ぐなら、OSだけではなくその手前のブートローダまで含めて考えないといけない、というのは将来の自分に言い聞かせたいことです。

> OSの入口を全部塞いでも、ブートローダが開いていればそこが入口になる。

## 脆弱性1の対策：U-Bootへのログイン認証付与

指摘を受けて、U-Bootコンソールに入る手前でパスワード認証を要求する対策を実施しました。

```text
┌──────────────────────────────┐
│ Hardware (SoC, eMMC)         │
└───────────────┬──────────────┘
                │
┌───────────────▼──────────────┐
│ U-Boot                       │
│   パスワード認証 ◄── 今回の対策 │
└───────────────┬──────────────┘
                │
┌───────────────▼──────────────┐
│ Linux Kernel                 │
└──────────────────────────────┘
```

### パスワードを環境変数で持つとザルだった

最初は、U-Bootの環境変数まわりでなんとかしようとしました。
ですが、これはすぐにダメだと分かりました。
環境変数は中身を参照できてしまううえに書き換えもできてしまうので、認証の設定そのものを無効化されるおそれがあるからです。

そこで最終的には、パスワードはハッシュ化したうえでビルド時にU-Bootバイナリへ持たせ、実行時の環境変数では無効化できない方式にしました。
地味ですが、「認証の設定を実行時に持たせない」というのがポイントだと思っています。

### FOTAで展開したら、ペンテスト機が再起不能に陥った

対策をしてみて一番感じたことは、対策そのものより、対策を配る仕組みのほうが怖い、ということです。

U-Bootはブートの根っこなので、アプリのアップデートのように気軽には差し替えられません。
とはいえ、出荷済みのデバイスにも展開する必要があるので、新しいU-BootをFOTA（Firmware Over The Air：リモートでのファームウェア更新）で更新できるようにしました。

ところが、FOTAで更新できるようにしたのち、実際にペンテストで使っていた実機へ展開した結果、その機体が再起不能に陥りました。
ブートローダが起動しないので、こうなるとリモートからは手の打ちようがありません。

仕方なく実機を引き上げて調査した結果、Shizen Box 2 は量産ロットによってeMMCのブートモードが異なり、FATモードで起動する個体とRAWモードで起動する個体が混在していたことが分かりました。
FOTAの更新処理はRAWモード前提で u-boot.img を書き込んでいたため、FATモードの個体では古いブートローダが残ったまま新しいU-Bootと食い違い、起動できなくなっていました。

| 個体 | 一次ローダ / u-boot.img の置き場所 |
|-----|--------------------------------|
| FATモードの個体 | eMMC第1パーティション（FAT）内のファイル |
| RAWモードの個体 | eMMCの特定セクタに直接 |

そこで、両方の個体に対応するために、ブートモードに応じて u-boot.img を展開するアドレス（書き込み先）を自動的に切り替えるようにしました。
イメージとしては以下のような感じです。

```bash
#!/bin/sh
# ※ デバイス名・オフセット・ファイル名はダミー。実値は伏せています
EMMC_DEV="<eMMCデバイス>"
PART1="${EMMC_DEV}p1"
MNT_DIR="/tmp/mnt_boot"

mkdir -p "$MNT_DIR"

if mount "$PART1" "$MNT_DIR" 2>/dev/null; then
    # FATモードの個体：パーティション内のファイルを更新
    cp /tmp/u-boot.img "$MNT_DIR/u-boot.img"
    sync
    umount "$MNT_DIR"
else
    # RAWモードの個体：eMMCの特定セクタへ直接書き込み
    dd if=/tmp/u-boot.img of="$EMMC_DEV" bs=512 seek=<オフセット> conv=notrunc
    sync
fi
```

これで両方の個体に正しく展開できるようになり、再起不能の問題は解消しました。

自分が把握していなかったロット差のようなものは、平時はまったく表に出てきません。
それがブートローダの更新のような戻せない操作をしたときに、一気に表面化するのが怖いところです。
フィールドへ展開する前にペンテスト機で試していたおかげで、フィールドで同じことが起きずに済んだのは不幸中の幸いでした。

## 脆弱性2：WebUIのIDORによる管理者パスワードの書き換え

- [CVE-2026-80254](https://www.cve.org/CVERecord?id=CVE-2026-80254)：ユーザ識別情報操作による権限チェック回避（CWE-639）
- CVSS v3.0：6.5（`CVSS:3.0/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`）
- CVSS v4.0：7.1（`CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:N/VI:H/VA:N/SC:N/SI:N/SA:N`）

### 何が問題だったか

IDOR（Insecure Direct Object Reference：安全でない直接オブジェクト参照）と呼ばれる種類の脆弱性です。
サーバ側が「リクエストで指定された対象」をそのまま信用して処理してしまい、ログイン中のユーザーにその対象を操作する権限があるかを確認していない、というものです。

今回は、パスワード変更の処理がまさにこれでした。
パスワード変更の対象となるユーザーの扱いに不備があり、本来の権限を越えて他のユーザーのパスワードを変更できてしまう状態でした。

先ほど書いた通り、WebUIは通常は外部から到達できない構成になっています。
なので、利用範囲がかなり限られた中での脆弱性で、リスクは低いと見ています。
とはいえ、ログインできるユーザーであれば権限の壁を越えられてしまうのは、直しておくべき問題でした。

### 対策：パスワードをセッションの認証ユーザーに紐づける

対策はシンプルで、パスワード変更時は、必ずセッションで確認済みの認証ユーザー情報と入力パスワードを紐づけて登録するように修正しました。

```text
# 対策後の考え方（概念図）
パスワード変更リクエスト
  → セッションで認証済みのユーザーに紐づけて、入力パスワードを登録
```

「誰のパスワードを変えるか」をクライアント側に決めさせず、サーバ側で確認済みの情報だけで決める、という考え方です。
こちらはU-Bootの件と違って、特にハマることもなく対策できました。

## さいごに

今回は、Shizen Box 2 に対して実施したペンテストの内容と、指摘された2件の脆弱性への対策を紹介しました。

事前に対策していたDoS攻撃や侵入への対策方針が功を奏して、通常の侵入経路はひと通り塞げていたことを確認できました。
第二回で紹介した守備固めがきちんと効いていたことが確認できたことが良かったです。

一方で、U-Boot経由でのファイルアクセスと、WebUIのIDORの2件については指摘を受けました。
ただ、ペンテストの中では、テスト機関がこれらの脆弱性を突いて機密情報の漏洩に至ることはありませんでした。
U-Bootの件は物理的にシリアルデバッグインタフェースへアクセスする必要があり、WebUIの件も通常は外部から到達できない構成で、テストのために到達可能にした状態で見つかったものなので、どちらも攻撃が成立する条件はかなり限定的だと考えています。

とはいえ、脆弱性は脆弱性なので、残しておく理由はありません。
どちらも対策を展開し、CVEとして登録完了しています（[JVN#91715694](https://jvn.jp/jp/JVN91715694/index.html)）。

> リスクが低いことと、対策しなくていいことは別。

振り返ってみると、今回の指摘はブートローダとWebアプリという、レイヤとしては両端に近いところに出ました。
U-BootからWebUIまで、どのレイヤの脆弱性でも自分たちで原因を切り分けて対策まで持っていけることが、私たちの強みだと思っています。
それができたのは、第一回で紹介したフルスタックの開発環境があったからで、連載の最初から最後までつながっていたなと改めて感じました。

今回はここまでです。
