## はじめに

組込み／IoT の結合テストを自動化しようとすると、テストスクリプトを書くだけでは済まないんですね。

仕様からテスト観点を拾って、ケースを作って、期待値を決めて、スクリプトにして、実機で動かして、結果を確認する。で、仕様変更が入れば、その一連の作業をまた追いかけることになります。

このあたりを生成 AI に手伝ってもらえれば、結合テストの準備から結果の整理まで、かなり助かりそうです。ただ、実機を操作するところまで考えると、「AI にどこまで任せるか」と「実機に触る権限をどこに持たせるか」を整理しておく必要があります。

そこで今回は、生成 AI を活用した IoT 結合テスト自動化フレームワークの構想を、モジュールの責務と関係が分かるくらいの粒度でまとめてみます。

まだ設計を整理している段階なので、実装や効果を検証した記事ではありません。特定企業の構成や機密情報を使わず、独立した Reference Architecture（参照アーキテクチャ）として考えています。

---

## まず、AI と実機操作の責務を分ける

AI にお願いしたいのは、仕様を読んでテスト観点を整理したり、ケースやスクリプトを作ったり、結果から問題点を拾ったりするところです。

一方で、テスト対象に接続するには SSH 鍵などの認証情報が必要になります。これを AI が扱える場所に置くと、生成したコードや会話、実行ログなどへ入り込む経路ができてしまいます。

なので、今回の構想では次のように責務を分けます。

* 人は、要求・目的を決め、各工程をレビューし、実機操作を承認する
* AI Agent と結合テストフレームワークは、Sandbox の中で動かす
* 実機への接続と操作は、Sandbox の外に置く Gateway が担当する

AI 側は「この操作をお願いします」と要求し、Gateway 側が「その操作を実行してよいか」を判断する、という関係です。

## 全体の構成

モジュール関連図にすると、こんな形になります。

```text
Human
 ├─ 要求・目的設定
 ├─ 各工程レビュー
 └─ 実機操作承認
          │
          ▼
┌──────── Sandbox ─────────┐
│ AI Agent                 │
│ Integration Test         │
│ Framework                │
│                          │
│ Test Analysis            │
│ Test Design              │
│ Test Implementation      │
│ Test Evaluation          │
│                          │
│ Credential = NONE        │
└──────────┬───────────────┘
           │ Capability API
           ▼
═══════ TRUST BOUNDARY ═══════
           │
┌──────────▼───────────────┐
│ Secure Execution Gateway │
│                          │
│ Authentication           │
│ Authorization            │
│ Policy Enforcement       │
│ Human Approval Check     │
│ Credential Management    │
│ Audit                    │
└──────────┬───────────────┘
           │ SSH/API/MQTT...
           ▼
┌──────────────────────────┐
│ Test Environment         │
│ IoT / Edge / Cloud       │
└──────────────────────────┘
```

図の矢印は、主に操作要求が流れる方向です。実行結果は Gateway を通して Sandbox 側へ戻し、テストの評価に使います。人の実機操作承認も、Gateway 側で確認します。

ちなみに `Credential = NONE` は、テスト対象へ接続するための SSH 鍵やパスワードなどを、AI Agent や Sandbox の中に持たせない、という意味です。

### Sandbox：テストを組み立てる場所

Sandbox には、AI Agent と結合テストフレームワークを配置します。

AI Agent は分析・設計・実装・評価を支援し、フレームワークはテスト手順の進行や結果の収集を担当します。ここからテスト対象へ直接接続する権限は持たせず、操作が必要になったら Capability API を通して要求します。

### Secure Execution Gateway：操作を受け付ける場所

Gateway は、Sandbox の外に配置します。役割は次のとおりです。

| 機能 | 役割 |
|------|------|
| Authentication | 誰からの要求かを確認する |
| Authorization | その要求元に操作を許可してよいかを確認する |
| Policy Enforcement | 定めた操作ルールを適用する |
| Human Approval Check | 必要な人の承認を確認する |
| Credential Management | テスト対象への接続用認証情報を管理する |
| Audit | 操作の記録を残す |

Gateway という名前にしていますが、単なる通信の中継ではありません。AI 側から来た要求を確認して、許可した操作だけをテスト環境へ渡す役目です。

### Test Environment：結合テストの対象

テスト対象は、IoT デバイス、エッジ側のソフトウェア、クラウド側のサービスなどを想定しています。

図の SSH／API／MQTT は接続手段の例です。どこまでを一つの結合テストで扱うかは、テストの目的に合わせて決めることになります。

## Capability API で、AI が要求できる操作を限定する

認証情報を AI から隠しても、Gateway に何でも実行させられるなら、操作の権限は広いままです。

そこで、AI 側から要求できる操作をあらかじめ限定する窓口として、Capability API を置きます。ここでいう Capability は、「実行を要求できる操作」くらいの意味です。

AI はこの窓口を通して操作を要求し、Gateway が権限・ポリシー・人の承認を確認します。AI がテストの都合で操作を追加したくなっても、それだけで実行可能な範囲が広がる構成にはしません。

図の TRUST BOUNDARY（信頼境界）は、この切れ目を表しています。Sandbox 側から来た要求は、Gateway 側で改めて確認する。AI の判断と、実行を許可する判断を分けておくわけです。

この境界は、図に線を引くだけでは成立しません。Sandbox 側から Gateway を迂回して実機に触れないようにする、というところまで含めて設計する必要があります。

## テスト工程は ISTQB の考え方を参考にする

テストの進め方は、ISTQB のテスト活動を参考に整理します。

ISTQB の CTFL シラバスでは、計画、モニタリングとコントロール、分析、設計、実装、実行、完了といった活動が整理されています。今回はこれを、AI と人の役割を分けるための「型」として使うイメージです。[ISTQB CTFL Syllabus v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

要求・目的設定を起点として、この記事では主な流れを次のようにまとめます。「評価」は結果の解釈と完了判断を含む、今回の構想上の呼び方です。

| 工程 | AI・フレームワークに任せること | 人が確認すること |
|------|------|------|
| テスト分析 | 要求からテスト観点を整理する | 要求の解釈や観点に抜けがないか |
| テスト設計 | ケースと期待結果を提案する | その条件と期待値で確認できるか |
| テスト実装 | 手順やスクリプトの作成を支援する | 設計した内容と合っているか |
| テスト実行 | Gateway 経由で操作し、結果を集める | 実行内容は妥当か、実機操作を承認してよいか |
| テスト評価 | 結果を整理し、問題点や考察を提示する | 根拠は十分か、どう評価するか |

全体図の Sandbox 内に Test Execution を独立して書いていないのは、実行の責務が二つに分かれるためです。テストの進行は Sandbox 内のフレームワークが管理し、対象への操作は Gateway が担当します。

## Human-in-the-Loop は各工程に置く

AI に一通り作ってもらって、最後に結果だけ見る形だと、最初の要求の読み違いまでそのまま下流へ流れてしまいます。

例えば期待値が間違っていれば、その期待値どおりにスクリプトが動いても、確認したかったことを確認できていない可能性があります。結果表がきれいに埋まっていると、かえって気づきにくいです。

なので、人が判断に入る Human-in-the-Loop（HITL）のポイントを、各工程に置きます。分析では観点、設計では期待値、実装では設計との整合、実行では実機操作の承認、評価では結果の解釈を確認する形です。

このレビューの配置は、今回の構想として決めているものです。ISTQB が、この承認構成を必須としているという意味ではありません。

AI が出した原因の説明についても、観測された事実と分けて確認したいところです。「こういう理由で失敗したと思う」という説明は、調査の入口にはなりますが、そのまま原因が確定したことにはならないので。

## 想定するリスクも、責務の分け方に対応させる

AI の誤判断に加えて、読み込む文書やログに不適切な指示が混ざることも考えておく必要があります。OWASP でも、Prompt Injection や、AI に過大な機能・権限・自律性を与える Excessive Agency が整理されています。[Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)、[Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

今回の構想では、リスクと対応を次のように考えています。

| 想定するリスク | 設計上の対応 |
|------|------|
| AI の誤判断や外部情報による不適切な指示 | 各工程のレビューと Gateway による実行制御 |
| 意図しない操作や過大な権限の利用 | Capability API による操作範囲の限定と認可 |
| テスト対象への接続用認証情報の漏えい | AI 側から分離して Gateway 側で管理 |
| 人の確認を経ない実機操作 | Gateway による承認確認 |
| 実行内容や評価根拠を後から追えない | 操作の記録と結果のレビュー |

もちろん、Gateway を置くだけですべて解決するわけではありません。Gateway 自体の保護や、何を許可するかの判断も必要になります。ここではまず、それぞれをどのモジュールが受け持つかを整理しています。

## おわりに

生成 AI を結合テストに使うなら、テストを組み立てるところから結果を整理するところまで、まとまった流れとして支援してもらいたいと思っています。

そのうえで、実機に触る権限と認証情報は Gateway 側に置き、人は各工程のレビューと操作の承認を担当する。この分け方を、フレームワークの土台にする構想です。

今回はモジュールの責務と信頼境界までの整理に留めています。どの製品や技術を使うかを決める前に、この役割分担をはっきりさせておくことが大事だと考えています。
