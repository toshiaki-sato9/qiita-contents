## はじめに

組込み／IoT の開発をやっていると、一番時間が溶けるのは実装よりも結合テストまわりだったりします。

クラウド、エッジアプリ、デバイス制御、通信インタフェース、異常系処理が絡んでくると、単体テストが全部通っていても「仕様通りに制御されるか」「通信が途絶えたときに安全側へ倒れるか」「異常値を入れて破綻しないか」「デグレしていないか」「SEGV やデッドロックが起きていないか」は、結局つないで動かしてみないと分かりません。

で、これを毎回手で回していると、仕様変更が入るたびにテスト設計を直して、ケースを直して、スクリプトを直して、結果表を直して……と、開発の速度がテストの追従速度に律速されるんですね。

これだけ開発効率に効くところなのに、Qiita や Zenn を探しても、組込みの結合テストを実機で自動化して運用まで紹介している記事はあまり見かけません。生成 AI に実機での実行まで任せる話となると、まだ PoC が出始めたくらいの段階です。

そこで、Claude Code をエンジンにして、機能仕様書からテスト結果までを一気通貫で同期できる結合テスト自動化フレームワークを作りました。テストのプロセスと成果物の切り方は ISTQB／JSTQB のフレームワークに沿わせています。今回はその考え方と仕組みについての備忘録です。

ちなみに用語の補足をしておくと、ISTQB（International Software Testing Qualifications Board）はソフトウェアテスト技術者資格の国際的な認定団体で、JSTQB（Japan Software Testing Qualifications Board）はその日本の加盟組織です。テストの用語やプロセスがシラバスとして体系化されていて、今回はこれを「型」として使っています。

## なぜ結合テストが開発のボトルネックになるのか

結合テストでは、スクリプトを自動実行できるだけではだいたい不十分です。

本当に手間がかかるのはテスト設計とテストケースのほうで、ここには仕様の理解、期待値、境界条件、異常系の考慮が入るので、人がレビューする必要があります。で、レビューで期待値や条件が変わると、その変更をテストスクリプトや結果管理まで追従させないといけない。ここを人手でやると、だんだんケースとスクリプトが乖離していって、「このスクリプト、何を確認してるんだっけ」状態になります。

なので今回は、人がやるべきこと（設計とケースのレビュー）と、機械に任せられること（下流への同期・実装・実行・記録）をはっきり分けて、後者を Claude Code に寄せる構成にしました。

> 人はレビューに集中し、同期と実行は Claude に任せる。これが開発を速くする一番の近道でした。

## ISTQB／JSTQB のテストプロセスに沿った構成

ISTQB のシラバスでは、テストプロセスを「テスト計画」「テストのモニタリングとコントロール」「テスト分析」「テスト設計」「テスト実装」「テスト実行」「テスト完了」といった活動に分けて整理しています。また、テストベース（テストの根拠になる仕様など）とテストウェア（テストケースやスクリプト、結果などの成果物）の間でトレーサビリティを確保することが重視されています。

今回のフレームワークは、この活動と成果物の区切りをそのまま使っています。

| ISTQB のテスト活動 | フレームワーク上の成果物 | Claude Code の役割 | 人の役割 |
|------|------|------|------|
| テスト分析 | 機能仕様書（テストベース）→ テスト条件 | 仕様からテスト条件を洗い出す | 抜け漏れのレビュー |
| テスト設計 | テスト設計書・テストケース | テスト技法を適用してケースを起こす | 期待値・境界・異常系のレビュー |
| テスト実装 | テストチェックリスト・テストスクリプト | ケースからスクリプトを生成・同期 | 差分の確認 |
| テスト実行 | テスト結果（テストログ） | 実行と結果の記録、ケースIDへの紐づけ | NG の原因判断 |
| テスト完了 | 結果サマリ | 集計・トレース表の更新 | テスト結果の共有 |

テスト設計では、ISTQB で定義されているテスト技法をベースに使っています。入力値なら同値分割と境界値分析、条件の組み合わせが効く制御ならデシジョンテーブル、通信状態や運転モードの遷移が絡むところは状態遷移テスト、という感じです。技法が決まっていると、Claude に「この仕様に境界値分析を適用して」と頼んだときの出力が安定しますし、レビューする側も「どの技法で、どの範囲を網羅したのか」という同じ物差しで見られます。

テストレベルとしては結合テスト（ISTQB でいう統合テスト）にあたり、エッジ側のプロセス間のインタフェースを主な確認対象にしています。クラウドとエッジの間（MQTT トピックの系）は、後で書くようにこのフレームワークのスコープからは外して、別途システム統合テストで確認する切り分けにしています。

## 一気通貫のトレース

フレームワークで一番重視したのは、以下の流れを一気通貫でトレースできることです。

```text
機能仕様書（テストベース）
  ↓  テスト分析
テスト条件／テスト設計
  ↓  テスト設計
テストケース
  ↓  テスト実装
テストスクリプト
  ↓  テスト実行
テスト結果
```

この各ポイント間の同期を、Claude Code のスキルとして用意しています。スキルはだいたい次のような単位で切っています。

* 隣り合うポイント間を同期する
* 指定ポイントを起点に、下流へ一気通貫で同期する
* 機能仕様書をテストベースとして、テスト技法に沿って網羅的にテスト設計する
* テストチェックリストとテストスクリプトを同期する
* テスト結果をテストケース単位で紐づける

スキルを ISTQB の活動単位で切っておくと、仕様変更やレビュー指摘が入ったときに「どこを起点に流し直せばいいか」がはっきりします。

例えば機能仕様書が変わった場合は、上流から全部流し直します。

```text
機能仕様書 → テスト設計 → テストケース → テストスクリプト → テスト結果
```

一方、テストケースのレビューで期待値だけ直った場合は、必要な範囲だけで済みます。

```text
テストケース → テストスクリプト → テスト結果
```

ここを人手でやると半日仕事になったりしますが、Claude に起点を指定して流してもらえば、人は出てきた差分を確認するだけで済みます。仕様変更から再テストまでの待ち時間がほぼなくなるのが、開発速度に一番効いているところです。

## 特徴1：SEGV 検出アラート

組込み Linux のアプリケーションだと、結合テスト中に SEGV（Segmentation Violation、不正なメモリアクセスによるプロセスの異常終了）が起きることがあります。

ただ、普通のテスト結果だけを見ていると、テストが失敗したのか、アプリが落ちたのか、通信が途絶えたのか、タイムアウトしたのかが区別しづらいんですね。

そこで、coredump を検出したら core ファイルを回収して、テスト結果に反映する仕組みを入れています。

```text
テスト実行
  ↓
coredump 検出
  ↓
core ファイル回収
  ↓
テストケースIDと紐づけ
  ↓
テスト結果へ SEGV 発生として記録
```

単なる NG ではなく、「どのテストケースでプロセスの異常終了が起きたか」まで追えるようになります。ISTQB でいうところのインシデント（欠陥）レポートの材料が、テスト実行の時点で揃っているイメージです。

## 特徴2：MQTT の代わりにプロセスインタフェースを叩く

本番の構成では、クラウドからの指示は MQTT トピック経由でエッジのアプリに届きます。ただ、結合テストフレームワークでは MQTT のブローカーは使わずに、対象プロセスが持っているプロセスインタフェース（プロセスへ直接コマンドを入れる口）を SSH のコマンド経由で叩いて、MQTT の受信処理の代わりにしています。このインタフェースはテスト用に足したものではなく製品にも載っている口なので、テストのための改造なしに、製品と同じ処理を通せるのが良いところです。

```text
テストケース
  ↓
SSH コマンド経由でプロセスIFへ入力（後述の認証ヘルパー経由）
  ↓
アプリ動作確認
  ↓
結果取得
```

最初は、テストケースごとに MQTT publish による入力と直接のコマンド入力を切り替えられる形で作っていました。ただ運用してみると、テスト用のブローカーを立てる分だけ、テスト用ネットワーク上に守るべき入口が1つ増えます。クラウド側から指示を出すなら、クラウドの認証情報もフレームワークに持たせることになるんですね。
なので、後からスコープを絞って MQTT の入力は外し、フレームワークでは「エッジ側のプロセス間インタフェース」だけを扱うようにしました。MQTT トピックの系（クラウド〜ブローカー〜エッジ）は、別途システム統合テストで確認します。ちなみにシステム統合テストは ISTQB のテストレベルの1つで、システムと外部のシステム（ここではクラウド）の間のインタフェースを確認するものです。

スコープを絞るときに気をつけたいのは、黙って外さないことです。テスト計画に「対象外」として明記して、システム統合テスト側のどのケースで確認するかを対応づけておかないと、MQTT の経路だけ誰もテストしていない、という状態になりかねません。

もう1つ、製品にも載っている口を叩くということは、その口が外からどう見えるかも合わせて考えておくべきです。

テストでは SSH 経由で叩けても、製品では端末の外から届かない（端末内のローカルからしか使えない）ことを前提にしておかないと、テストのための経路がそのまま攻撃の経路になってしまいます。

## 特徴3：テスト結果の自動反映

テスト実行後は、各テストケースに対して以下の情報を自動で記録します。

| 項目 | 内容 |
|------|------|
| 実行日時 | テストを流した日時 |
| テストケースID | テスト設計・仕様へ戻るためのキー |
| 入力条件 | 入力値と入力IF |
| 期待値 | テストケースに書かれた期待値 |
| 実測値 | 実際の出力・状態 |
| 判定結果 | OK / NG / SEGV など |
| ログファイル | 実行時ログへのパス |
| coredump 有無 | 異常終了の有無と core ファイル |
| 備考 | 補足事項 |

テストケースIDをキーにしているので、結果からテストケース、テスト設計、機能仕様書まで逆向きにたどれます。後からレビューするときに「なぜ NG だったのか」を追いやすいのは地味に重要です。

## 課題と対策：認証まわりの基盤を先に入れておく

運用してみて一番気をつけないといけないと感じたのが、テスト対象機器への認証情報の扱いです。

結合テストでは、テスト対象の実機に SSH でログインして、ログや core ファイルを回収したり、プロセスにコマンドを入れたりします。当然 SSH の認証情報が必要になるわけですが、パスワードを平文で設定ファイルや環境変数に置いておくと、Claude Code がスクリプトを生成・実行する過程でその値を読めてしまいます。読めるということは、会話のコンテキストに載ったり、生成したスクリプトやログにうっかり埋め込まれたりする可能性がある、ということなんですね。

じゃあパスワードを暗号化して、復号鍵を別の場所に置けばいいかというと、それだけでは足りません。復号するテストランナーを動かしているのが Claude 自身なら、Claude は復号鍵を使えてしまうので、平文を取り出すこともできてしまいます。

で、Claude が動かしているプロセスに認証情報を持たせている限り、どう暗号化しても隠し切るのは無理があります。なので、認証情報は Claude とは別の OS ユーザーで動く「認証ヘルパー」だけが扱い、Claude はそのヘルパーに「どの端末で何を実行するか」を頼むだけ、という形に分けるべきだと考えています。そのうえで、万一漏れたり悪用されたりしても被害が出ない認証情報にしておく、という2段構えです。

もう1つ大事なのが順番です。結合テストフレームワークを動かし始めてから個別に対策を足していくと、どこかに「とりあえずパスワードで」が残りがちです。なので、フレームワークを運用する前にテスト専用の認証基盤を入れておき、フレームワークはその基盤の上でしか動かない形にしておくべきです。

### 推奨モデル：テスト専用 CA と短期の SSH 証明書

軸にするのは OpenSSH の証明書認証です。あまり知られていない気がしますが、OpenSSH には CA（Certificate Authority、認証局）の鍵で公開鍵に署名して「証明書」にする仕組みがあって、接続先はその CA を信頼しておけば、個別の公開鍵を `authorized_keys` に配って回らなくても済みます。証明書には有効期限、使える端末（principals）、接続元を埋め込めるので、「この端末に、この場所から、数時間だけ入れる」認証情報を実行のたびに発行できます。

```text
Claude Code（OS ユーザー: claude）
  鍵・証明書・ssh-agent のソケットには一切触れない
  ↓ 許可されたコマンド1つだけ（sudo）、またはローカルソケット
認証ヘルパー（OS ユーザー: 認証専用、root 所有・署名つきバイナリ）
  - 受け取るのは「対象端末」と「実行するコマンド」だけ
  - テスト用 CA が発行した短期証明書と、固定した ssh_config で接続
  - 環境変数をクリアし、対象端末の許可リストと実行前チェックを通らなければ止める
  - すべての接続をログに残す
  ↓
テスト端末（テスト用 CA の証明書しか受け付けない）
```

基盤としては、だいたい次のような層で考えています。

| 層 | 中身 | ねらい |
|------|------|------|
| 本番との分離 | テスト用 CA を本番と分け、テスト端末がクラウドにつなぐ証明書も本番とは分けたテスト環境用のものにする。テスト用のアカウントや CA 公開鍵は製品イメージに含めない。テスト端末はテスト用ネットワークに閉じる | 漏れても出荷個体・フィールド稼働個体・本番の接続先には影響させない |
| 発行 | 短期のユーザー証明書を実行のたびに発行し、対象端末・接続元・期限を埋め込む。失効の手順も用意しておく | 1つ漏れても、使えるのは限られた端末・限られた時間だけにする |
| 端末側 | テスト用 CA だけを信頼し、パスワード認証・root ログイン・エージェント転送を切る。ホスト証明書も入れておく | 基盤の証明書以外では入れないようにする。リフラッシュ後の known_hosts の更新もいらなくなる |
| 実行時 | 証明書と ssh-agent は認証ヘルパーの OS ユーザーだけが持ち、Claude はヘルパー経由でしか接続できないようにする | Claude の手元に、使える鍵も agent も置かない |
| 監査 | 証明書の発行記録、ヘルパーの接続ログ、端末側の認証ログを残す | 何かあったときに追えるようにする |

ssh-agent を Claude 側に置く形（Claude が `SSH_AUTH_SOCK` 経由で接続する形）も考えられますが、それだと鍵を持ち出されないだけで、agent が生きている間は Claude が自由にどこへでも接続できてしまいます。agent ごとヘルパー側に寄せておけば、Claude にはヘルパーを通る以外の接続手段がなくなるので、対象端末の制限やログの記録をヘルパーで一括して強制できます。ちなみに、SSH の多重化（`ControlMaster`）の制御ソケットが残っていると証明書の期限が切れた後も接続できてしまうので、ヘルパー側では使わないか、期限内で切れるようにしておきます。

ただ、ヘルパーを通せば Claude はテスト端末上でコマンドを実行できるので、これで「何もさせない」状態になるわけではありません。最終的には、テスト端末・テスト用ネットワーク・短い期限の中で被害が閉じる状態を作っておくのが本命です。

### 認証ヘルパーを変更できない形で通させる

基盤を入れたら、結合テストフレームワークからは必ず認証ヘルパーを通して実行させて、Claude からも利用者からも認証オプションを変えられない運用にしておくべきです。

最初は「認証まわりをバイナリやライブラリにして固めれば変更できなくなるのでは」と考えたんですが、それだけだと片手落ちなんですね。理由はいくつかあります。

- バイナリが守れるのはバイナリを通った接続だけで、Claude が `ssh` を直接叩いたり Python の paramiko でつないだりすれば素通りになる
- ライブラリだと、呼び出す側のテストランナーは Claude が書いているので、呼ばない・引数を変える・monkeypatch で差し替える、ができてしまう
- 変更できないかどうかはバイナリかどうかではなく、ファイルの所有者と権限、署名の検証で決まる
- `LD_PRELOAD` や `PATH`、`~/.ssh/config` のような外側の設定で挙動を変えられる
- バイナリに認証情報を埋め込むと `strings` で取り出せるので、むしろ逆効果

なので、バイナリ化は「ヘルパー自体を改ざんさせない」ための1つの層として使い、ほかの層と組み合わせて強制する形にしています。Claude Code の権限設定で `ssh` の直接実行を deny にするのも、`bash -c` や subprocess 経由で迂回できるので補助扱いです。

| 層 | 強制のしかた |
|------|------|
| テスト端末側（本命） | テスト用 CA の証明書以外では入れない。テスト用アカウントは root にせず、sshd の設定を書き換えられない権限にする |
| OS 側（権限の分離） | 証明書と ssh-agent は認証専用の OS ユーザーだけが持ち、Claude Code は別の OS ユーザーで動かす。Claude からはヘルパーの呼び出し1つだけを許可する |
| 認証ヘルパー自身 | root 所有・読み取り専用・署名つきのバイナリにし、実行前に署名やハッシュを検証する。認証情報は埋め込まず、環境変数をクリアして固定した設定だけで動く。ビルド・署名・更新できる人を決めておく |
| Claude Code 側（補助） | 管理者が配布する managed settings で、`ssh` の直接実行、`.claude/` 配下の設定・フック・スキルの書き換え、権限確認をスキップするモードを禁止する。外向き通信もサンドボックスの許可リストで絞る |
| フレームワーク側 | 実行前チェックでヘルパーの署名と証明書の有効性を確認し、満たさなければテストを開始しない |

最後の実行前チェックは fail-closed（条件を満たさなければ止める側に倒す）にしておくのが大事で、こうしておけば「認証基盤を通らない結合テスト」はそもそも走りません。

ここは自動化を進めるほど見落としやすいところで、生成 AI にテストの実装と実行まで任せるなら、「Claude に何を読ませないか」「どの経路でしか接続させないか」も設計の一部として最初に決めておくべきだと感じました。

> Claude に任せる範囲を広げるほど、Claude に渡さない情報の線引きが重要になる。

## その他、セキュリティ面で気をつけておきたいこと

SSH の認証情報以外にも、Claude に結合テストを回させるなら押さえておくべきところがいくつかあります。

| 懸念 | 何が起きうるか | 対策の方向性 |
|------|------|------|
| テスト環境から本番に届いてしまう | 設定ミスや生成されたスクリプトで、テスト端末やフレームワークの接続先が本番を向き、フィールドの実機制御に入ってしまう | フレームワークにはクラウドの認証情報を持たせず、MQTT のブローカーも使わない。テスト端末の認証情報では本番に接続できないようにし、テスト用ネットワークから本番の接続先への通信自体を通さない |
| Claude の権限が広すぎる | 自動承認の範囲が広いと、ファイル削除、フラッシュ書き換え、再起動、機器の出力変更を Claude の判断で実行できてしまう | 実行してよいコマンドを許可リストで絞り、破壊的な操作や物理機器を動かす操作は人の承認を挟む。機器側にも安全上の上限やインターロックを持たせる |
| テスト結果が「通るように」書き換えられる | NG のとき、スクリプトではなく期待値やテストケースのほうを直して OK にしてしまう | 期待値の変更は git の diff を人が必ずレビューし、テスト実行の段階ではテストケースを読み取り専用にする |
| coredump やログに機密情報が残る | core ファイルにはプロセスのメモリがそのまま入るので、クラウドの認証トークンや証明書の秘密鍵が含まれうる | 保管場所のアクセスと保管期間を絞り、Claude には core を丸ごと読ませずバックトレースなどの解析結果だけを渡す。ログの認証情報はマスクする |

特に1つ目は、蓄電池や太陽光のような物理的な機器を制御する組込み開発だと影響が大きいので、最優先で考えておくべきところです。

3つ目はセキュリティというより品質保証の信頼性の話ですが、地味に効いてきます。せっかく ISTQB に沿って機能仕様書からテスト結果までトレースできるようにしても、期待値が黙って書き換えられたらそのトレース自体が信用できなくなるんですね。Claude は「テストを通す」ことには熱心なので、期待値を変えてよいのは人のレビューを通ったときだけ、というルールはフレームワーク側で強制しておくべきだと考えています。

---

## 作ってみて分かったこと

結合テスト自動化で大事なのは、スクリプトを書くことそのものではなかったです。

仕様とテスト設計がつながっていて、テストケースとスクリプトが乖離せず、レビューで変わった期待値が追跡できて、結果から仕様へ戻れること。で、SEGV のような異常終了もちゃんとテスト結果として扱えること。このあたりが揃って初めて、テストが開発のブレーキではなくなる感覚があります。

ISTQB／JSTQB の型に乗せたのも効いていて、活動と成果物の区切りが標準に沿っていると、Claude への指示も、人のレビュー観点も、チーム内の会話もブレにくくなります。生成 AI にテストを書かせるとき、「何をどこまで任せるか」の境界線を引く物差しとして、テストプロセスの標準はかなり相性が良いと感じました。

> 速くするために自動化するのではなく、仕様変更に追従し続けられるから速くなる。

---

## まとめ

今回、Claude Code を使って、機能仕様書からテスト結果までを一気通貫で同期できる結合テスト自動化フレームワークを作りました。テストの分析・設計・実装・実行は ISTQB／JSTQB のテストプロセスに沿って区切り、それぞれを Claude Code のスキルとして回しています。

人はテスト設計とテストケースのレビューに集中し、下流への同期、スクリプト生成、実行、結果記録は Claude に任せる。この分担で、仕様変更から再テストまでのリードタイムを縮めて、組込み開発全体のスピードを上げるのが狙いです。

ただ、Claude に実行まで任せる以上、Claude が動かすプロセスに SSH の認証情報を持たせない設計が必要です。なので、フレームワークを運用する前に、テスト専用 CA で短期の証明書を発行する認証基盤を入れておき、結合テストは Claude とは権限を分けた認証ヘルパーを通してしか実行できないようにしておくべきです。

今後は、CI/CD との連携や、PR 単位でのデグレ検知にも広げていきたいと思っています。
