こんにちは。Shizen Connectの佐藤です。

私は現在エネルギーマネジメントシステムを支えるエッジ端末「Shizen Box」を開発しています。

昨年、Shizen Boxは第三者ペネトレーションテスト（以下、ペンテスト）を実施しました。本連載では、私がペンテスト対応した実務経験をもとに、設計・実装・運用の観点で得られた知見を整理しています。

### 第二回の内容

今回はペンテスト実施前に行った対策について備忘録を紹介します。

ざっくり実施したことは

1. 不要なサービス・プロセス・ポートを無効化
2. ファイアーウォールによる明示的な通信制御
3. カーネルレベルでのDoS攻撃への耐性
4. 物理インタフェースの封鎖
5. 侵入を試みられた場合の早期検知対策

結果として、ペンテスト実施前の段階で攻撃対象となり得る入口を最小限に抑えることができ、実際のペンテストにおいても有効な防御層として機能していたことを確認しました。

また、本記事で紹介する対策は、ペンテスト対応だけでなく、Shizen Boxが取得しているJC-STAR★1認証要件への対応も兼ねています。

> **JC-STAR（Japan Cybersecurity Standards, Certification Scheme for Advanced & Trusted IoT）**
> 一般社団法人環境共創イニシアチブが定める IoT 機器のサイバーセキュリティ認証制度です。★1 は基礎的なセキュリティ要件を定めており、本記事で紹介する対策の多くが認証要件に直接対応しています。

---

## 1.不要なサービス・プロセスを無効化する

組み込み Linux 開発では、高価な商用Linuxを使わない限り、ベンダー提供の汎用BSP（Board Support Package：ボードサポートパッケージ）をベースに自社向けの rootfs を構築するケースが多いと思います。
この汎用BSP には、製品用途では不要なパッケージやサービスが初期状態で含まれていることが少なくありません。
攻撃者の観点では、不要なサービスが稼働しているだけで侵入の起点になるので、不要なサービスの削除は地味に重要です。

確認には主に以下を使用しました。

```bash
ps aux
systemctl list-units --type=service
netstat -tulnp
```

不要と判断したサービス・パッケージは**rootfs ビルド時点で除外**し、運用時に停止するのではなく「存在しない状態」としました。
この対応は、JC-STAR ★1 要件における**「不要なサービス・ポートを開放しないこと」**にも直接対応します。

## 4.物理的インタフェースの封鎖

論理的なインタフェースだけでなく、物理インタフェースも重要な侵入口です。
フィールドに設置されたデバイスにシリアルコンソール経由でアクセスできる状態は、物理的に接触できる攻撃者にとって大きな侵入口になります。
JC-STAR 要件においても、「全ての未使用の物理的インタフェース及び論理的インタフェースは無効化しなければならない」と定められていますが、シリアルコンソールを封鎖すべしと明示されているわけではありません。
Shizen Boxでは、シリアルコンソール経由でのログインを、キッティング検査完了時に無効化する設計としています。

### 実装方法

具体的にはキッティング検査完了時に、シリアルコンソールから以下を実行することで無効化しています。

```bash
# シリアルコンソールの無効化
systemctl mask <serial-ttyサービス>
```

この設定により、シリアルポートからの対話的ログインができなくなります。なので封鎖したシリアルポートを再度開くスクリプトを用意することも重要になります。

### 状態遷移の設計

* **製造・検査時**: シリアルコンソール有効（検査用）
* **キッティング完了後**: シリアルコンソール無効化を実施
* **再検査時**: 特定の手順により一時的に復帰可能

キッティング後の再検査が必要なケースに備えて、製造拠点でのみ使用可能な復帰手順を用意しています。
これにより、フィールドでの物理アクセスによる不正ログインリスクを低減しつつ、メンテナンス性を維持する設計としています。

## 5. 侵入を試みられた場合の早期検知対策

これは、一般家庭向けの製品でもあるShizenBoxへ侵入がどれほど試行される可能性があるのか？
確認のために導入した仕組みです。
具体的には、ポートへのアクセス試行が試みられたことを検知して、Slackで通知する機能を導入しています。
侵入検知はiptablesのLOGを特定ポートに設定し、アプリケーションからLOGを監視することで実現しています。

## おわりに

セキュリティ対策は、侵入されてから対処するだけでは不十分です。

Shizen Boxにおける守備固めは、「入られない」だけでなく、「入口を作らない」「触ったら分かる」設計を意識して実施しました。ただし、すべてを完璧に不可視にすることよりも、攻撃者が侵入を試みたときに確実に検知・防御できる実用的な構成を優先した点は、第一回の開発環境構築と同様に、理想よりも実運用での確実性を重視した判断でした。

IoT / 組み込みデバイスのセキュリティ対策に向き合っている方の参考になれば幸いです。
